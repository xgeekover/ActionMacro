# tools — 실기기 점검 스크립트

`tests/` 의 자동 테스트는 화면 없는 Qt(offscreen)에서 pynput·mss 를 가짜로 바꿔 돈다. 그래서 **실제 데스크톱에서만 생기는 문제**는 잡지 못한다.
2026-10-24 처음 실기기에서 돌렸을 때, 테스트 727개가 모두 통과한 상태에서 앱이 **클릭·키 단계 시작 순간**과 **긴급 정지 리스너가 켜지는 순간** 강제 종료됐다
(pynput 이 macOS 키보드 입력 소스 API 를 메인 스레드 밖에서 불러 SIGTRAP). 입력 · 단축키 · 좌표 피커 · 엔진의 스레드 구조를 고친 뒤에는 아래 점검을 돌린다.

> ⚠️ 이 스크립트들은 모두 **실제 마우스·키보드를 움직인다.** 도는 동안 손을 뗀다. (Windows 판은 3절부터)

## 필요한 권한 (macOS — 점검을 실행하는 터미널 앱에)

시스템 설정 → 개인정보 보호 및 보안:
- **손쉬운 사용** — 마우스·키 입력을 보낸다
- **입력 모니터링** — 전역 단축키 리스너와 키 이벤트 기록

화면 기록 권한은 필요 없다(화면을 캡처하지 않는다).

## 1. 자동 점검 — `device_check_macos.py` (약 20초)

```bash
.venv/bin/python tools/device_check_macos.py                 # 전체 점검
.venv/bin/python tools/device_check_macos.py --stop-key-trials 10   # 키 누르는 도중 정지만 10번 반복
```

| 점검 | 통과 기준 |
|---|---|
| 클릭 정밀도 — 모니터마다 10회 (왼쪽·위쪽 모니터의 음수 좌표 포함) | 오차 ≤ 1px |
| 더블클릭 (clicks=2) | Qt 가 더블클릭으로 받음 |
| 긴급 정지 — 연속 클릭 · 3초 클릭 누르기 · 3초 키 누르기 도중 | 50ms 뒤 새 입력 0건, 100ms 안에 눌린 것 해제 |
| **실제 메인 창** — 시작 버튼 → 클릭 (전역 단축키 리스너 켜짐) | 충돌 없음, 정확한 위치 클릭, 실행 중 리스너 살아 있음 |
| 조합키 — `shift+a`, `cmd_or_ctrl+a`, down/up, 예전 파일의 `modifiers` | OS 가 받은 키 이벤트 순서(앞 키 누른 채 → 마지막 키 → 역순 해제) |
| 좌표 피커 — 모니터마다 | 찍은 좌표 = 클릭한 좌표 |
| 전역 단축키 리스너 | 이벤트 탭 스레드가 살아 있음 |

결과는 화면에 `[PASS]/[FAIL]/[SKIP]` 으로 찍히고 `device_check_report.json` 에 단계마다 저장된다. 종료 코드: 0 통과, 1 실패 있음, 3 감시 시간 초과.
충돌하면 133(SIGTRAP — `~/Library/Logs/DiagnosticReports/python3*.ips` 확인) 또는 139(SIGSEGV — `<report>.crash.txt`).

### 안전 장치
- 클릭 직전마다 **그 좌표의 맨 위 창이 점검 프로세스의 창인지** 확인하고, 아니면 그 단계를 건너뛴다(SKIP).
- 키 입력은 **점검 창이 맨 앞 앱이고 입력란에 포커스가 있을 때만** 보낸다. 키 단계마다 다시 확인한다.
- 키 이벤트는 수신 전용 이벤트 탭으로 기록하되 **점검 프로세스가 보낸 이벤트만** 남긴다. 사용자가 직접 치는 키는 기록하지 않는다.
- 120초(`--timeout`)가 넘으면 눌린 입력을 모두 풀고 스스로 끝난다. 끝나면 커서를 원래 자리로 돌린다.

## 2. 직접 누르는 긴급 정지 — `device_check_hotkeys_macos.py` (대화형)

전역 단축키 리스너는 프로그램이 보낸 키를 일부러 무시하므로, "사람이 Esc 를 누르면 멈춘다"는 사람이 눌러야만 확인된다.

```bash
.venv/bin/python tools/device_check_hotkeys_macos.py
```

메인 창이 뜨고 **대기만 반복하는 무한 매크로**(입력을 보내지 않는다)가 돈다. 안내가 나오면:
1. **Esc** 를 한 번 — 어느 창에 포커스가 있든 상관없다.
2. 약 1.5초 뒤 매크로가 다시 시작되면 **Ctrl+Shift+S** 를 한 번.

기록하는 것은 이 두 키를 누른 시각뿐이다. 종료 코드: 0 둘 다 멈춤, 1 기대와 다름, 2 시간 초과(기본 240초).

## 알아 둘 점 (2026-10-24 실측, macOS 26.6 · 외장 1배 모니터 2대)

- **한글 입력기(두벌식)** 상태에서는 매크로가 보낸 `a` 키가 입력란에 `ㅁ` 으로 찍힌다 — 사람이 눌러도 같다. 키 이벤트 자체는 정확하다(점검은 이벤트로 판정한다). 게임에 따라 한글 상태에서 키가 먹지 않을 수 있다.
- 엔진은 실행이 끝날 때마다 **누르지 않은 ctrl/alt/shift/cmd 까지 무조건 놓는다**(이벤트 열 끝의 4개). 점검은 이것을 떼어 내고 판정한다.
- 독(Dock)과 알림 센터는 화면 전체를 덮는 투명 창이라 맨 위 창 판정에서 뺀다. 대신 클릭 목표는 화면 아래 200px 위에 둔다.
  macOS 27 에서는 알림 센터 창이 레이어 21 이 아니라 **23** 에서 주 화면을 늘 덮는다(2026-10-31, macOS 27.2). 23 을 모르던 점검은 주 화면 단계 7개를 SKIP 했다.
- 앞서 충돌한 프로세스의 **"Python이 예기치 않게 종료되었습니다" 경고창**이 남아 있으면 그 자리 클릭은 SKIP 된다. 닫고 다시 돌린다.
- 실행 직후 시스템 키 상태가 몇 ms 동안 '눌림'으로 읽힐 수 있다 — 정지 판정은 400ms 시점의 상태로 한다.
- 엔진은 목표로 커서를 옮긴 뒤 **그 순간의 커서 위치에서** 버튼을 누른다. 점검 중 마우스·트랙패드가 살짝 움직이면 받은 좌표가 소수점만큼 어긋난다
  (한 번은 0.9px, 커서는 1~3px 밀림 — 기준 1px 안). 크게 움직이면 클릭이 빗나갈 수 있으니 손을 뗀다.

| 기준선 결과 | 값 |
|---|---|
| 클릭 오차 (주 모니터 · 왼쪽 보조 모니터 음수 좌표) | 0px (손을 뗐을 때) |
| 긴급 정지 — 실행 스레드 종료 / 버튼·키 해제 | 1.5~7ms |
| 직접 누른 Esc / Ctrl+Shift+S | 24ms / 1ms 미만 |

## 3. Windows 자동 점검 — `device_check_windows.py` (약 30초)

macOS 점검과 같은 구성(드라이버를 주입하지 않은 엔진을 GUI 스레드에서 `start_async()`)이고, **글자 입력(Send: Text)** 점검이 먼저 돈다. 권한 설정은 필요 없다.

```powershell
.venv\Scripts\python tools\device_check_windows.py                     # 전체 점검
.venv\Scripts\python tools\device_check_windows.py --text-only         # 글자 입력만
.venv\Scripts\python tools\device_check_windows.py --text-only --states hangul,caps
.venv\Scripts\python tools\device_check_windows.py --context-menu-only # 오른쪽 클릭처럼 보이는 키
```

| 점검 | 통과 기준 |
|---|---|
| 글자 입력 — `myid123`, `Ab1 x_Y!@`, `안녕하세요 홍길동 id123`, 줄바꿈(LF·CRLF)·탭이 든 문자열 × 한/영 영문 · 한글 · Caps Lock 켬 · 한글+Caps Lock | 입력 칸의 글자 = 단계의 글자, 실행 뒤 IME 모드·Caps Lock 그대로 |
| WM_IME_CONTROL 로 창의 IME 모드 읽기·바꾸기 | ImmGetConversionStatus 와 일치 |
| 조합키 · 키 누르는 도중 정지 · 클릭 정밀도(모니터마다) · 더블클릭 · 클릭 도중 정지 · 실제 메인 창 · 좌표 피커 · 단축키 리스너 | macOS 점검과 같다 |
| `menu` · `shift+f10` Key Input 단계 | 판정 없이 기록(INFO): 컨텍스트 메뉴 요청이 생기는지 |

- 한글 상태는 점검 창 자신의 입력 컨텍스트에 `ImmSetConversionStatus`(안 되면 기본 IME 창에 `WM_IME_CONTROL`)로 IME_CMODE_NATIVE 를 켜서 만든다. 둘 다 안 되면 `--manual-ime` 로 한/영 키를 눌러 달라고 묻는다. Caps Lock 은 주입한 Caps Lock 키로 켠다. 끝나면(실패·감시 시간 초과 포함) 둘 다 원래대로 돌린다.
- 안전 장치: 클릭 직전 그 좌표의 최상위 창(WindowFromPoint → GetAncestor)이 점검 프로세스 것인지, 키 직전 전경 창이 점검 프로세스 것이고 입력 칸에 포커스가 있는지 확인한다. 키 기록은 저수준 키보드 훅에서 **주입 이벤트(LLKHF_INJECTED)만** 남긴다. 다른 프로세스 창은 클래스 이름만 기록한다(제목 없음). 120초(`--timeout`)가 넘으면 입력을 풀고 IME·Caps Lock 을 돌린 뒤 끝난다.

## 4. Windows 직접 누르는 긴급 정지 — `device_check_hotkeys_windows.py` (대화형)

macOS 판과 같다(무한 대기 매크로 → Esc → Ctrl+Shift+S). 주입되지 않은 두 키를 누른 시각만 기록한다.
지금 누를 키는 화면 위쪽의 안내 창(항상 위)에 나온다. 백그라운드로 실행하면 콘솔 출력이 보이지 않기 때문이다.
**Claude Code 등 터미널에 포커스가 있으면 Esc 가 그 터미널로 간다** — 누르기 전에 메인 창을 클릭해 둔다.

## 알아 둘 점 — Windows (2026-10-31 실측, Windows 10 22H2 · 모니터 1대 2560×1440 배율 100%, 1920×1080 배율 125% · Microsoft 한국어 IME)

- **한/영이 한글 상태여도 글자 입력은 그대로 들어간다.** 한 글자씩 보내는 KEYEVENTF_UNICODE 패킷(VK_PACKET)은 한국어 IME 를 거쳐도 바뀌지 않는다(점검 창의 Qt 입력 칸, 패키지 → 메모장 둘 다). macOS 와 달리 입력하는 동안 영문으로 바꾸는 장치가 필요 없다. Caps Lock 켬에서도 같다.
- 줄바꿈과 탭만 실제 Enter·Tab 키로 간다. CRLF 는 Enter 한 번.
- 배율 125% 첫 실행에서 한 번, 영문 상태의 `안녕하세요 홍길동 id123` 이 패킷 15개를 다 보냈는데 칸에 "안"만 들어갔다. 원인은 모른다. 그 뒤 같은 PC 에서 영문 5회 반복과 전체 점검(네 상태)을 다시 돌렸을 때는 재현되지 않았다. 지금 점검은 글자가 늦게 들어오면 2초 더 기다리고, 0.4초 시점의 글자, 받은 방식(키 이벤트 / IME 확정), 단계 직후 전경 창·포커스를 남긴다. 다시 나오면 `--text-only --states english --repeat 10` 으로 모은다.
- 한국어 IME 는 영문으로 바꾸면(IME_CMODE_NATIVE 끔) IME open 상태도 함께 꺼진다. 점검은 open + NATIVE 를 한글로 본다.
- **Caps Lock 을 한/영으로 바꾸는 프로그램**(AutoHotkey `CapsLock::` 등)이 돌고 있으면 주입한 Caps Lock 도 한/영으로 바뀐다. 점검은 이를 알아보고 그 상태를 SKIP 한다 — 재매핑을 잠시 멈추고 `--states caps,hangul_caps` 로 다시 돌린다.
- 백그라운드 셸에서 띄운 창은 전경 잠금 때문에 다른 창 뒤에 뜰 수 있다. 점검 창은 항상 위(topmost)이고, 첫 클릭(점검 창 위인지 확인한 뒤)으로 전경이 된다.
- `menu`(VK_APPS)와 `shift+f10` Key Input 단계는 **오른쪽 클릭과 같은 컨텍스트 메뉴**를 연다. `cmd`/`win` 이 든 단계(`cmd+x` 등)는 Windows 에서 Win 키 조합이다 — Win+X 는 시작 버튼 오른쪽 클릭 메뉴, Win+V 는 클립보드 기록 창.
- **Windows 의 클릭 좌표는 물리 픽셀이다.** 엔진(pynput)과 화면 캡처(mss)가 물리 픽셀을 쓰고, Qt 는 배율로 나눈 논리 좌표를 쓴다(125% 에서 1920×1080 화면이 1536×864). 그래서 좌표 피커는 Windows 에서 물리 픽셀을 돌려준다 — 배율 125% 에서 고치기 전에는 찍은 점 (805, 455) 을 클릭하면 (644, 364) 에 떨어졌다(161px). 고친 뒤 같은 PC 에서 피커 → 클릭 단계 왕복 오차 0.2 논리 px, 클릭 정밀도 0px. macOS 는 Qt 좌표가 곧 클릭 좌표라 그대로다.
- 배율이 100% 가 아닌 Windows 화면에서 0.1.1 이하의 피커로 찍은 좌표는 논리 좌표라 엉뚱한 곳을 누른다 — 다시 찍는다. 100% 에서 찍은 좌표는 그대로 맞다.
- 점검 자신의 클릭(입력 칸 포커스, 피커 클릭)은 점이 그려진 물리 픽셀로 가고, 클릭 단계에는 피커가 줄 물리 픽셀을 넣는다. 배율이 100% 가 아니면 클릭 판은 작업 영역 전체를 덮어, 빗나가도 점검 창 위에 떨어지게 한다.
- 음수 좌표·다중 모니터·배율 150% 는 아직 재지 못했다(모니터 하나).
- **자동 테스트를 Windows 에서 돌리면**(`QT_QPA_PLATFORM=offscreen`) 다 통과하고, 다음만 건너뛰거나 예상 실패로 나온다: offscreen 플러그인에 시스템 글꼴이 없어 글꼴·패널 폭 검사 5건 SKIP(실제 플러그인 `QT_QPA_PLATFORM=windows` 로는 통과), POSIX 권한 2건 SKIP, 열린 파일을 `os.replace` 로 못 바꾸는 동시 읽기·쓰기 1건 XFAIL, macOS 전용 4건 SKIP(2026-10-31, GitHub Actions windows-latest). 이 실행은 이제 `.github/workflows/tests.yml` 이 main push 와 PR 마다 돌린다(macOS 러너는 스레드가 25~75ms 늦게 깨어나 실제 플러그인 레이아웃·글꼴 검사만 돌린다). 결과 개수는 실행의 JUnit 산출물(`junit-*`)에서 읽는다 — `gh run view --log` 은 잘려서 요약 줄이 빠질 수 있다.

| Windows 기준선 | 값 |
|---|---|
| 클릭 오차 (주 모니터, 배율 100% · 125%) | 0px |
| 피커 → 클릭 단계 (배율 125%) | 0.2 논리 px |
| 긴급 정지 — 실행 스레드 종료 / 버튼·키 해제 | 19.5ms / 3~5ms |
| 직접 누른 Esc / Ctrl+Shift+S | 12ms / 9.6ms |

## 아직 없는 것
- **이미지 인식(실제 화면 캡처)** 점검 — 터미널 앱에 화면 기록 권한이 필요하다.
- **레티나 화면** — macOS 기준선은 1배 모니터에서 쟀다. Windows 는 위 "알아 둘 점" 참고.
